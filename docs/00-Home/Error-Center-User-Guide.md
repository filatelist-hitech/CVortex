# Error Center: что делать, когда CVortex показывает ошибку

Error Center помогает найти техническую причину сбоя по **Reference ID**. Он не исправляет данные автоматически и не заменяет проверку результата операции. Интерфейс доступен только активному администратору CVortex. Обычный пользователь видит безопасное сообщение об ошибке и передаёт его код и Reference ID администратору.

## Если ошибка возникла у вас

1. Запишите **код ошибки**, **Reference ID** и примерное время. Reference ID выглядит как идентификатор запроса; в сообщениях API он стоит после `Reference:`. Если ID не показан, запишите время и действие, которое выполняли.
2. Прочитайте действие в сообщении. Если есть подсказка `You can retry`, повторите операцию после проверки её текущего результата. Не отправляйте одну и ту же форму много раз подряд.
3. Если ошибка повторяется, передайте администратору код, Reference ID, время и краткое название действия, например «извлечение фактов из текста». Не отправляйте пароль, API-ключ, полный текст резюме или вакансии ради диагностики.

| Что видно в CVortex | Что делать |
|---|---|
| `VALIDATION_FAILED` | Проверьте поля формы и показанные рядом замечания. Это ошибка ввода, обычно без записи в Error Center. |
| `AUTH_REQUIRED` или `PERMISSION_DENIED` | Войдите снова или обратитесь к администратору за доступом. Повторная отправка той же формы права не изменит. |
| `RATE_LIMITED` | Подождите и повторите позже. Не запускайте серию одинаковых запросов. |
| `LLM_OUTPUT_INVALID` | CVortex отклонил результат генерации при серверной проверке; это не ошибка введённых вами данных. Не отправляйте запрос повторно без подсказки Retry. Передайте Reference ID администратору. |
| `PROVIDER_ERROR` или `LLM_PROVIDER_UNAVAILABLE` | Проверьте текущий статус операции. При сбое извлечения Career Facts можно добавить подтверждённый факт вручную. Повторяйте только если ответ явно помечает сбой как retryable; иначе передайте Reference ID администратору. |
| `GENERATION_UNAVAILABLE` или `VALIDATION_UNAVAILABLE` без подсказки о повторе | Provider или модель требуют настройки. Не отправляйте операцию снова; передайте Reference ID администратору. |
| `INTERNAL_ERROR`, `CAREER_OPERATION_FAILED`, `VACANCY_OPERATION_FAILED` | Проверьте, сохранился ли результат. Повторяйте только если интерфейс предлагает Retry для retryable-сбоя; передайте Reference ID администратору. |
| `Page unavailable` или `Application unavailable` | Нажмите `Retry`, затем при необходимости `Reload`. Если страница снова падает, передайте показанный Reference и время. |
| Сообщение о проблеме соединения с `NETWORK_ERROR` | Проверьте доступность локального CVortex и сети. Такой сбой может не иметь серверного Reference ID или записи в Error Center. |

У сбоя страницы Reference иногда является локальным идентификатором Next.js (`digest`), если браузер не смог отправить диагностическое событие. Такой идентификатор может **не находиться** в поиске Error Center. В этом случае администратору нужны время и название страницы. Отсутствие инцидента само по себе не доказывает, что ошибки не было.

## Как администратору найти инцидент

1. Войдите под активной учётной записью `admin`. В шапке рабочего пространства нажмите `Diagnostics` или откройте `/diagnostics`. Это отдельная страница администратора; обычный пользователь не видит ссылку и не получает данные API.
2. Вставьте точный Reference ID, `job ID`, `LLM run ID`, `application ID` или `error code` в главный поиск — вставка запускает поиск сразу. Поиск не ищет по произвольному тексту. `Clear search` очищает только запрос; `Clear all` сбрасывает применённые фильтры.
3. Быстрые фильтры — статус, важность, компонент и период 24 часа / 7 / 30 дней. `More filters` раскрывает provider, service, environment, error code, даты и отдельные идентификаторы. Provider сравнивается с провайдером **последнего сохранённого появления**; это точный фильтр, а не поиск по тексту. На узком экране быстрые и расширенные поля находятся в одной прокручиваемой панели, а Apply/Clear all закреплены внизу. Применённые фильтры видны в чипах и удаляются по одному. Период и даты относятся к **последнему появлению**. По умолчанию выше открытые инциденты с большей важностью; сортировку можно поменять. Сводные числа с подписью «on this page» относятся только к текущей странице, `Matching incidents` — к полному результату запроса.
4. Список показывает понятный заголовок операции, классифицированную причину, статус, частоту и время; класс исключения и UUID там скрыты. Откройте инцидент и сначала прочитайте **Cause → Impact → Recommended action → Retryable**. Это сведения из стабильного кода ошибки и сохранённой безопасной метаинформации, а не AI-объяснение. Диагностика **не подтверждает**, были ли изменены данные: при сомнении проверяйте результат операции отдельно. Не нажимайте повтор до устранения указанной причины.
5. `Correlation` показывает только записанные связи и позволяет копировать полный ID или безопасную сводку. В `Recent occurrences` каждая запись раскрывается отдельно; общий счётчик может быть больше двадцати доступных деталей. Для browser runtime incidents там также показан полный сохранённый `Browser error reference`, который можно скопировать. Для provider 429 блок Retryable показывает сохранённый интервал `Retry after N seconds` либо честное `Retry delay was not recorded.` При другой временной ошибке провайдера интервал показан только если провайдер его передал. Не угадывайте время ожидания по отсутствующему значению. `Technical details` и framework frames закрыты по умолчанию. Время показано относительно и точной локальной меткой с часовым поясом; мобильная строка сохраняет дату и время.
6. `Previous`/`Next` переключают страницы по 25 групп, `Reload` обновляет текущую страницу. Если поиск вместе с фильтрами пуст, нажмите `Clear filters and search again`: введённый ID сохранится. Если пуст только поиск, проверьте точность ID, срок хранения и локальные логи. При недоступности Error Center используйте операторский fallback. `Retry` повторяет именно неудачную загрузку списка, открытие деталей либо изменение статуса и появляется только при `retryable=true` в API.

### Что означают статусы

| Статус | Когда использовать | Что происходит при повторе той же ошибки |
|---|---|---|
| `OPEN` | Причина ещё исследуется или сбой повторяется. | Счётчик растёт, статус остаётся `OPEN`. |
| `RESOLVED` | Причина устранена и результат проверен. | Инцидент автоматически снова станет `OPEN`. |
| `IGNORED` | Событие осознанно принято и не требует работы сейчас. | Счётчик продолжит расти, статус останется `IGNORED`; пересматривайте решение вручную. |

Во время смены статуса кнопки блокируются и показывается `Saving…`; результат объявляется на экране. Эффективная смена записывается в аудит, повторная отправка уже установленного статуса не создаёт второй записи. `RESOLVED` — пометка для команды, а не проверка здоровья внешнего провайдера, очереди или пользовательского сценария.

## Типовые сценарии

**Не удалось извлечение или анализ через LLM.** Пользователь сообщает Reference ID. Администратор ищет его в `search`, открывает инцидент и сверяет `Job`, `LLM`, `Provider` и `Attempt`. `FAILED` у самой операции и запись в Error Center относятся к одному сбою, но статус инцидента не меняет статус операции. Ключи и текст запроса провайдеру в Error Center не выводятся.

**Одинаковый сбой случился много раз.** Error Center группирует его в одну строку. Используйте `occurrence count`, `first seen`, `last seen` и последние обращения, чтобы отличить разовый случай от продолжающегося. Один инцидент не означает одного затронутого запроса.

**У пользователя упала страница.** Сначала попросите нажать `Retry` или `Reload`. Если браузер успел отправить диагностическое событие после входа, ищите Reference ID и код `FRONTEND_RUNTIME_ERROR`. Если записи нет, уточните время: событие до входа, проблема сети или недоступность PostgreSQL могли помешать сохранению.

**Ошибка ввода или отказ в доступе.** Исправьте поля либо доступ. Обычные `4xx` ошибки не создают инцидент. Reference ID всё равно помогает сопоставить ответ с серверным запросом, пока соответствующий лог доступен.

**Поиск ничего не нашёл.** Проверьте точность ID, сбросьте другие фильтры и попробуйте код ошибки с интервалом времени. История обращений ограничена сроком хранения и примерно тысячей последних записей на группу; старый ID может исчезнуть, хотя общий счётчик остаётся. Если PostgreSQL недоступен, Error Center тоже недоступен — оператор использует локальные логи по [операционной инструкции](../10-Operations/Logging-and-Diagnostics.md).

## Доступ, хранение и границы

- Обычный пользователь не может читать чужие диагностические записи или менять их статус. Администратор видит технические идентификаторы пользователей и очищенные кадры стека, поэтому не пересылайте скриншоты деталей в открытые каналы.
- Error Center по умолчанию показывает все сгруппированные предупреждения и ошибки, но не полный поток `DEBUG`/`INFO` и не журнал действий. Для сырых логов контейнеров оператор использует команды из [операционной инструкции](../10-Operations/Logging-and-Diagnostics.md); такие строки могут содержать служебные сведения.
- По умолчанию отдельные обращения старше 30 дней удаляются; закрытые (`RESOLVED`/`IGNORED`) группы без новых появлений удаляются после 90 дней. Открытые группы сохраняются, но их старые детали очищаются. Локальные Docker-логи ротируются отдельно и не являются архивом.
- Здесь нет автоматических уведомлений, отправки отчётов наружу или публичной страницы статуса. Для команд, API-контрактов и восстановления см. [Logging and Diagnostics](../10-Operations/Logging-and-Diagnostics.md) и [OpenAPI diagnostics](../05-API/diagnostics.openapi.yaml).
