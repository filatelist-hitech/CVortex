# Phase 06 Security Threat Model

External vacancies, recruiter messages, uploads, HTML/web/API responses and tool output are **untrusted data, never instruction**. The matrix records each threat's own asset and threat source; global categories are not substitutes for the per-threat boundary.

| Threat | Asset | Threat actor / source | Attack surface and scenario | Impact | Preventive controls | Detective controls | Residual risk | Validation / testing strategy |
|---|---|---|---|---|---|---|---|---|
| Prompt injection | trusted instructions, authorized context, truth of candidate content | malicious vacancy, recruiter message, website, upload or tool output | Injected text attempts to override workflow, invoke tools or exfiltrate context | false facts, disclosure, unsafe action | separate trusted prompt/data; minimal owner-scoped context; policy-gated tools; schema and Truth Guard; M1.4 labels vacancy and Career context as untrusted data and exposes no submission tool | safe LLM-run audit; policy/validation failure telemetry | semantic evasion | adversarial vacancy/message/upload fixtures; assert no tool/action/context escape |
| SSRF | internal services, metadata endpoints, network availability | malicious URL/source | Future fetcher follows URL, redirect or DNS rebinding to private address | private-data disclosure, pivot, outage | allowlisted protocols/sources; DNS/IP private/link-local validation; redirect revalidation; time/size limits; isolated egress | request/egress logs; blocked-target alerts | DNS races and parser defects | redirect, encoding, DNS-rebind and blocked-range tests |
| XSS | browser session, rendered candidate/external content | malicious HTML/rich text or generated text | Imported or generated markup executes in a browser | session/data theft, unauthorized actions | render as text; escape by default; sanitize at boundary; CSP | sanitizer decision/error logs; CSP reports | sanitizer bypass | malicious-markup regression fixtures and browser rendering tests |
| File traversal | private storage, converter host, generated files | malicious filename, archive entry or generated path | Path escapes storage root or reaches unintended parser file | file disclosure/overwrite, host compromise | opaque generated names; normalized storage references outside webroot; ownership checks; isolated converter | rejected-path/security logs; converter alerts | parser zero-days | traversal, symlink, archive-path and malformed-file tests |
| IDOR | an individual private resource | authenticated malicious user | Guessed identifier or nested route accesses another resource | unauthorized read/write/delete | server-side resource authorization; non-enumerating denial; explicit audited admin operation | authorization-denial and anomaly audit | missed new endpoint/query | negative read/write/delete/nested-route tests |
| Cross-user access | tenant-scoped aggregates, queues, cache, files and AI context | authenticated user, buggy worker or cache consumer | Owner scope is omitted or forged across relation/job/cache/context | bulk PII and career-content leakage | authenticated server-derived owner; same-owner relation checks; scoped queue/cache/file/context keys | cross-tenant access alerts; correlation audit; anomaly review | missed propagation path | User A vs User B matrix for list, relation, job, file, cache and context selection |
| Malicious uploads | parser/converter availability and stored files | hostile uploaded PDF/DOCX/archive | Spoofed MIME, macro, bomb or malformed parser input consumes or exploits worker | code execution, outage, unsafe file | inspect bytes; quarantine; reject/limit macros, archives and size; resource/time limits; sandbox parser | quarantine/parser failure metrics and alerts | parser vulnerabilities | bomb, spoofed MIME, macro and corrupt-file fixtures |
| Secret leakage | provider keys, BYOK credentials, system secrets | developer/operator mistake, log/export consumer, malicious input | Secret appears in logs, prompt, export, audit or document | account takeover, spend and data exposure | encrypted storage; redaction; masked display; no post-store client return; least privilege | secret-scanning/redaction alerts; credential lifecycle audit | operational error | log/prompt/export/audit redaction tests |
| PII leakage | career/application data, backup/export and provider context | over-broad workflow, provider, backup or unauthorized operator | Excessive context transfer, insecure export or restore exposes private data | privacy breach and loss of trust | context minimization; owner scope; retention/deletion/export policy; encrypted access-controlled backups; provider review | context-size/access logs; restore/export audit | provider or backup compromise | context minimization and restore/export access tests |
| LLM credentials | system and BYOK credential material, provider budget | attacker with stolen key or cross-user credential path | Credential resolution, rotation or provider request uses wrong owner/key | provider misuse, spend and user data exposure | encrypted-at-rest owner-scoped resolution; no prompt/log/client round trip; rotate/delete; least privilege | usage anomaly monitoring; resolution failures; add/rotate/delete audit | valid-key abuse | tenant resolution, rotation, revocation and no-secret-in-run tests |
| OAuth redirect URI | authorization codes and tokens returned to external/native clients | malicious DCR client or crafted URI | Host confusion, userinfo, scheme confusion, malformed authority or dot-segment/encoded-path traversal changes the callback destination | authorization-code or token disclosure | DCR parses URI components; exact external host/scheme/port and fixed callback path shape; loopback-only HTTP with exact callback path and dynamic port; reject userinfo, query, fragment, percent-encoded path, malformed URI and descendants | DCR regression matrix through the registered `/oauth/register` route | client-controlled local listener and future callback-policy drift | exact approved external callback; IPv4/IPv6/localhost loopback; host, scheme, port, traversal, encoding and URI-structure attacks |

Security validation is required before each future ingestion, fetcher, parser, credential or context implementation; human approval does not mitigate a failed technical control.

## Diagnostics extension (2026-09-27)

Admin-only incident APIs expose sanitized operational metadata and bounded stack frames; normal users cannot enumerate them. Browser telemetry is authenticated and rate limited, validates fixed kinds, finite components and a route allowlist, ignores raw message/stack and derives user identity server-side; an opaque reference derived from error name and numeric stack locations appears only on the bounded occurrence. Every configured Laravel logging channel applies the structured redactor before its handler. Nginx access logging uses an explicit JSON field allowlist with URI path only, omitting query strings, request targets and headers; infrastructure error logs remain a separate boundary. Raw stderr logs and queryable incidents have independent failure paths; incident persistence errors cannot replace the original application error. Tests exercise cross-role access, untrusted telemetry, sink failures and fake-secret canaries.

## MCP Gateway extension (2026-09-27)

The disabled-by-default [MCP Gateway](../02-Architecture/MCP-Gateway.md) is an external **read-only** boundary with exactly `vacancy_get` and `application_context_get`. OAuth bearer scope, active-user enforcement, owner-scoped queries/RLS, strict schemas, bounded output and rate limiting address token misuse, IDOR and excessive disclosure. Vacancy-derived text stays untrusted data. MCP exposes no mutation, approval, fact-review, application-state, message-send, arbitrary URL, filesystem, SQL, shell or secret access. OAuth uses authorization code + PKCE, strict parsed redirect validation, issuer/resource-bound access tokens and bearer-only MCP POSTs; browser cookies do not authenticate MCP.

Read calls are covered by before/after product-state assertions for application preparations/drafts, approvals, applications, Career Facts, Claims, vacancy status/snapshots, employer memory and LLM runs. Tests also cover active/invalid/revoked/expired credentials, missing scope, owner/foreign IDs, incomplete and failed analysis, bounds and untrusted vacancy instructions. Secure MCP Tunnel keeps the listener private but MCP requests, arguments, responses and applicable OAuth artifacts cross OpenAI infrastructure; `CONTROL_PLANE_API_KEY` authenticates the local tunnel client and must stay outside the repository, logs and chat. On 2026-10-03 the Plus ChatGPT web account displayed the custom MCP app form and resolved an existing Platform tunnel. The form draft was not submitted; `tunnel-client` is installed locally but cannot authenticate because the runtime key is not configured. App entitlement and ChatGPT Desktop tool invocation remain unverified. `APP_DEBUG=false` is required in production; safe client responses do not establish that local framework logs contain no additional exception detail.

### Local OAuth origin boundary — 2026-10-03

Local Secure MCP Tunnel transport target and OAuth issuer/endpoints use `http://127.0.0.1:8080`. The OAuth resource identifier for the selected Tunnel is configured separately through existing `MCP_RESOURCE_URL`, using one exact deployment-controlled value observed in its authorization request. That same resource is required on authorize/token/refresh and in the signed bearer resource claim; another tunnel, the direct-local identifier, missing resource and arbitrary input remain rejected. Issuer/client audience, signature/revocation, PKCE, redirect URI, scopes and owner isolation remain enforced. Configuration is not accepted from user content or request Host/body. No outbound URL fetcher or SSRF surface is added. Harpoon HTTP opt-in is limited operationally to this trusted loopback setup; do not add arbitrary trusted origins, public proxies or payload logging. Existing PKCE, strict redirect/scope/resource/issuer and bearer checks remain intact; imported content remains untrusted.

Browser OAuth authentication failures now show a login guidance page only for Passport's GET authorize route and non-JSON requests, after the authorization request has passed Passport validation. Links use configured issuer endpoints, not inbound Host/forwarded headers or an arbitrary return URL. Existing first-party login is used in a new tab; continuing requires the user's authenticated session and explicit consent. The page uses no-store/no-referrer and Blade escaping. JSON/API and MCP guest denial remain unchanged. Consent accurately declares read-only access.

The first-party access form explicitly specifies POST and disables submission until React hydration, preventing the default native GET from exposing credentials in query strings when JS fails. The dev-server origin exception is limited to canonical `127.0.0.1`; no wildcard or production auth exception is added. Historical accidental GETs can still leave credentials in browser history/dev logs and require password rotation; do not reproduce those URLs in diagnostics.
