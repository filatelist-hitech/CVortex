# Локальная установка и запуск CVortex

В этой инструкции разберём, как развернуть CVortex на рабочей машине через Docker Compose. Документ рассчитан строго на локальную разработку и не предназначен для боевого деплоя на публичные серверы.

## Что понадобится

Из системных зависимостей понадобятся только Git, Make и Docker с плагином Compose. Убедитесь, что демон Docker Engine или приложение Docker Desktop запущены. Ставить PHP, Composer, Node.js, npm, PostgreSQL и Redis на хост-систему не требуется: всё крутится в изолированных контейнерах. Для форматированного вывода логов командой `make logs-pretty` пригодится Python 3.

## Первый запуск

В чистой копии репозитория выполните:

```sh
git clone https://github.com/filatelist-hitech/CVortex.git
cd CVortex
make init
docker compose --env-file .env config --quiet
make up
make migrate
```

Что делают эти команды:

- `make init`: если локального `.env` ещё нет, команда скопирует `.env.example`, сгенерирует `APP_KEY`, пароль суперпользователя PostgreSQL и отдельный пароль ограниченной роли приложения. Затем соберёт образы и подтянет зафиксированные зависимости в Docker-тома. Если `.env` уже существует, текущие значения сохранятся; пустой или совпадающий с админским пароль роли приложения скрипт заменит на уникальный.
- `docker compose --env-file .env config --quiet`: валидирует итоговый Compose-манифест. Если команда ругается на ошибки синтаксиса или переменных, не запускайте контейнеры до устранения нестыковок.
- `make up`: поднимает все службы в фоновом режиме (detached).
- `make migrate`: инициализирует ограниченную роль `cvortex_app` и накатывает миграции базы через разовый сервисный контейнер.

После запуска обязательно проверьте готовность сервисов:

```sh
docker compose ps
health_authority="$(docker compose port nginx 80)"
curl -fsS "http://${health_authority}/api/v1/health/ready"
```

Когда всё поднялось штатно, `/api/v1/health/ready` вернёт HTTP 200 и `{"status":"ready"}`. После этого переходите в браузер по адресу `APP_URL` из `.env` (по умолчанию `http://127.0.0.1:8080`). Дефолтных аккаунтов «из коробки» нет: создание первого администратора и генерация инвайтов описаны в руководстве [«Доступ и первый вход»](M1-Access-Core.md).

## Переменные окружения

Воркер Horizon работает в двух Docker-сетях: внутренней `internal` (для связи с PostgreSQL и Redis) и изолированной `egress` (для исходящих вызовов к LLM-провайдеру). Сеть `internal` изолирована (`internal: true`), наружу порты Horizon не публикуются. PostgreSQL, Redis и шедулер остаются строго во внутреннем контуре. При изменении сетевых настроек пересоздайте контейнер командой `docker compose up -d --no-deps horizon`.

Чтобы быстро проверить DNS, TLS и сетевую связность с API OpenAI без расхода токенов и передачи данных, выполните:

```sh
docker compose exec -T horizon curl --connect-timeout 10 --max-time 20 -sS -o /dev/null -w 'HTTP %{http_code}\n' https://api.openai.com/v1/models
```

Ответ HTTP 401 подтверждает, что исходящий сетевой путь работает штатно (OpenAI отбил неавторизованный запрос, но само соединение установлено). Этот тест не проверяет баланс, валидность вашего API-ключа или доступность конкретных моделей. Повторный глубокий анализ вакансии всегда передаёт данные наружу и требует явного подтверждения пользователя.

Файл `.env.example` содержит безопасные дефолты для локального контура и пустые плейсхолдеры для секретов. Никогда не коммитьте в Git боевые пароли, API-ключи, инвайт-токены или персональные карьерные данные. Команда `make init` генерирует локальные секреты прямо на месте — не копируйте рабочий `.env` между разными машинами.

| Переменная | Для чего нужна |
|---|---|
| `CVORTEX_PORT` | Порт, на котором Nginx доступен только на этом компьютере; по умолчанию `8080` |
| `APP_URL` | Адрес, который нужно открыть в браузере; он должен соответствовать порту и имени узла |
| `POSTGRES_DB` | Имя базы данных в подключённом томе PostgreSQL |
| `POSTGRES_USER`, `POSTGRES_PASSWORD` | Учётные данные администратора PostgreSQL и миграций; они должны соответствовать значениям, с которыми был создан существующий том |
| `POSTGRES_RUNTIME_USER`, `POSTGRES_RUNTIME_PASSWORD` | Отдельная ограниченная учётная запись для службы `backend` (сервера приложения) и Horizon; пароль создаёт `make init`, он должен отличаться от пароля администратора |
| `AI_PROVIDER` | ИИ-провайдер; по умолчанию `none`, текущий адаптер OpenAI включается значением `openai` |
| `OPENAI_API_KEY` | Ключ доступа; нужен только при `AI_PROVIDER=openai` |
| `OPENAI_BASE_URL` | Адрес API; по умолчанию используется официальный API OpenAI |
| `OPENAI_CAREER_EXTRACTION_MODEL` | Модель для извлечения фактов о карьере и требований вакансии |
| `OPENAI_APPLICATION_DRAFT_MODEL` | Модель для подготовки и проверки черновиков; Compose передаёт значение в `backend` и Horizon |
| `OPENAI_APPLICATION_INPUT_COST_MICROS_PER_MILLION_TOKENS` | Стоимость входных токенов выбранной модели черновиков в микродолларах за миллион токенов; нужна для оценки стоимости |
| `OPENAI_APPLICATION_OUTPUT_COST_MICROS_PER_MILLION_TOKENS` | Стоимость выходных токенов выбранной модели черновиков в микродолларах за миллион токенов; нужна для оценки стоимости |
| `MCP_ENABLED` | Входящий MCP Gateway; по умолчанию выключен (`false`) и не нужен для обычной работы с Preview |

Чтобы изменить порт, задайте согласованные значения `CVORTEX_PORT` и `APP_URL` в `.env`:

```dotenv
CVORTEX_PORT=18080
APP_URL=http://localhost:18080
```

Затем примените изменения:

```sh
make up
```

По умолчанию сервис ИИ отключён. Базовый функционал доступен и без него: можно вручную вносить и подтверждать факты, а также просматривать профиль. Для первого разбора вакансии ИИ необходим — модель вычленяет требования из сырого текста. После этого сопоставление с подтверждённым опытом кандидата работает по внутренним детерминированным правилам. Если требования вакансии уже сохранены в базе, повторный анализ запускается без новых вызовов к нейросети. Ручной ввод требований вакансии пока в разработке. Для извлечения фактов из текста резюме и генерации черновиков откликов требуется подключённый провайдер и корректно указанные модели. Полная конфигурация лежит в `apps/backend/config/ai.php`.

Чтобы включить генерацию откликов, укажите в корневом `.env`: `AI_PROVIDER=openai`, передайте `OPENAI_API_KEY` и модель `OPENAI_APPLICATION_DRAFT_MODEL`, после чего выполните `make up` для обновления настроек `backend` и Horizon. Чтобы система могла рассчитывать ориентировочную стоимость запросов, задайте обе переменные стоимости токенов (`OPENAI_APPLICATION_INPUT_COST_MICROS_PER_MILLION_TOKENS` и `OPENAI_APPLICATION_OUTPUT_COST_MICROS_PER_MILLION_TOKENS`). Если одна из них пропущена, калькуляция останется пустой. Держите ключ только в локальном `.env`.

## Остановка, запуск и обновление

| Действие | Команда | Что произойдёт |
|---|---|---|
| Запустить остановленные службы | `make up` | Запустит контейнеры в фоне |
| Остановить службы | `make down` | Удалит контейнеры и сеть, но сохранит тома PostgreSQL и закрытых файлов |
| Перезапустить службы | `make restart` | Остановит и запустит контейнеры заново; тома сохранятся |
| Обновить схему базы | `make migrate` | Применит миграции к локальной базе |

Порядок обновления исходного кода в репозитории:

```sh
git status --short
git pull --ff-only
make init
docker compose --env-file .env config --quiet
make up
make migrate
```

Перед обновлением проверьте рабочее дерево: `git pull --ff-only` не станет сливать разошедшиеся ветки с незакоммиченными правками. Команда `make init` обновит образы и зависимости, а `make migrate` применит свежие миграции к базе данных. Обратите внимание: в репозитории пока нет единого скрипта резервного копирования и восстановления базы или закрытых файлов. Не удаляйте Docker-тома вслепую и не рассчитывайте, что Git сохранит ваши пользовательские данные.

## Если приложение не запускается

### Страница открывается, но проверка готовности возвращает 503

`/api/v1/health/live` проверяет прохождение HTTP-запроса через Nginx и Laravel. Эндпоинт `/api/v1/health/ready` копает глубже и валидирует доступность PostgreSQL и Redis. Проверьте статус контейнеров и снимите логи:

```sh
docker compose ps
make logs SERVICE=backend
make logs SERVICE=postgres
make logs SERVICE=redis
```

Бывает, что контейнер PostgreSQL в `docker compose ps` помечен как healthy, но бэкенд не может до него достучаться: например, если указанной в `POSTGRES_DB` базы попросту нет внутри подключённого тома.

### Появилось сообщение `database "…" does not exist`

Такое случается, если в `.env` указано имя базы, отличное от того, с которым изначально инициализировался Docker-том PostgreSQL. Не спешите сносить том: остановите контейнеры и посмотрите список реальных баз:

```sh
make down
make up
docker compose exec -T postgres sh -lc \
  'psql -U "$POSTGRES_USER" -d postgres -Atc "SELECT datname FROM pg_database ORDER BY datname;"'
```

Если данные лежат в базе с другим именем, просто пропишите актуальное имя в `POSTGRES_DB` внутри `.env`. Не меняйте логины и пароли наугад: том мог быть создан с другими кредами. Перепроверьте манифест и накатите миграции:

```sh
docker compose --env-file .env config --quiet
make up
make migrate
```

Если нужной базы в списке нет, проверьте, к какому проекту Compose и какому именно тому привязаны данные. **Категорически избегайте `docker compose down --volumes` в попытке починить ошибку:** эта команда безвозвратно сотрёт базу данных и приватные файлы.

### Порт уже занят

Пропишите в `.env` свободный `CVORTEX_PORT` и синхронизируйте `APP_URL`, затем перезапустите стек через `make up`. Не убивайте незнакомые системные процессы только ради того, чтобы освободить порт 8080.

### Контейнер нездоров или операция завершается ошибкой

Выполните `docker compose ps` и запросите логи проблемной службы: `backend`, `postgres`, `redis`, `frontend` или `horizon` через `make logs SERVICE=<имя>`. Если ошибка выскочила в интерфейсе, передайте администратору код ошибки и `Reference ID`. Подробности разбора инцидентов собраны в руководствах [«Разбор ошибок»](../00-Home/Error-Center-User-Guide.md) и [«Журналы и диагностика»](Logging-and-Diagnostics.md).

## Хранение данных и доступ из сети

Данные PostgreSQL и приватные файлы из каталога `storage/app/private` сохраняются в именованных Docker-томах. Содержимое Redis намеренно не персистится. Единственная служба, публикующая порт наружу — это Nginx, причём он жёстко привязан к интерфейсу `127.0.0.1`. Остальные сервисы доступны исключительно внутри виртуальной сети Compose. Не пробрасывайте порт в локальную сеть или интернет через роутер без настройки защиты.

Карьерные факты, тексты вакансий и черновики содержат чувствительные персональные данные. Они спокойно переживают команды `make down`, `make restart` и `make up`. А вот `docker compose down --volumes` гарантированно снесёт базу и хранилище файлов. Логи Docker ротируются и перезаписываются: они не заменяют полноценный архив или бэкап.

## Полезные команды оператора

| Команда | Назначение |
|---|---|
| `make test` | Запустить тесты сервера и веб-интерфейса, а также проверить включение и выключение маршрутов MCP |
| `make lint` | Проверить формат PHP-кода, PHP-анализатор, правила кода веб-интерфейса и типы TypeScript |
| `make logs SERVICE=backend` | Показать последние 200 строк журнала выбранной службы |
| `make logs-pretty SERVICE=backend` | Удобно отформатировать JSON-журнал; на компьютере должен быть Python 3 |
| `make failed-jobs` | Показать окончательно завершившиеся ошибки очереди через систему диагностики |
| `make diagnostics-prune` | Удалить записи диагностики, срок хранения которых истёк |
| `make shell SERVICE=backend` | Открыть командную оболочку внутри работающего контейнера |
| `make shell SERVICE=backend COMMAND='php -v'` | Выполнить одну команду внутри контейнера |

Полный список проверок служб приведён в [операционной инструкции M0](M0-Runbook.md), схема контейнеров показана в документе [«Локальный запуск M0»](../02-Architecture/M0-Runtime.md).

## Дополнительная настройка MCP

Входящий шлюз MCP Gateway по умолчанию отключён. Если включить его вручную, открываются только два read-only инструмента: `vacancy_get` и `application_context_get`. Править факты, менять черновики или их статусы через этот шлюз невозможно. Для Inspector, OAuth и Secure MCP Tunnel требуются отдельные ключи, эндпоинты издателя токенов и явные права. Обычному пользователю настраивать это не требуется. Локальный сценарий интеграции с ChatGPT разобран в [руководстве по подключению ChatGPT](ChatGPT-CVortex-Local-Setup.md).

Архитектурные ограничения зафиксированы в [ADR-0021](../03-ADR/ADR-0021-inbound-mcp-read-only.md), схеме [MCP Gateway](../02-Architecture/MCP-Gateway.md) и [инструкции по валидации](MCP-Gateway-Validation.md). Не выставляйте Gateway в открытый интернет без должной конфигурации и тестирования.

## Гидратация frontend-интерфейса на loopback

В режиме разработки Next.js требует явного разрешения канонического loopback-хоста в `next.config.ts`: текущая конфигурация прописывает `127.0.0.1` через `allowedDevOrigins` без масок и подстановок. Если при попытке входа форма откатывается к нативному GET или обработчики React не подхватываются, загляните в консоль браузера на предмет ошибок загрузки ресурсов и перезапустите службу `frontend`. Форма логина отправляет POST-запрос и блокирует сабмит до завершения гидратации, чтобы учётные данные не улетели в адресную строку. Для проверочной production-сборки используйте изолированное монтирование `.next`, чтобы не портить кэш работающего dev-сервера:

```sh
docker compose run --rm --no-deps -e NODE_ENV=production -v /app/.next frontend npm run build
```
