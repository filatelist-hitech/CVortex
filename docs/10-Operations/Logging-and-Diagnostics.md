# Журналы и диагностика

Оперативный гайд по расследованию инцидентов и работе с логами в локальном окружении Docker Compose. О пользовательских сценариях и интерфейсе центра ошибок читайте в [руководстве по разбору ошибок](../00-Home/Error-Center-User-Guide.md), а спецификацию защищённых эндпоинтов смотрите в [OpenAPI-контракте диагностики](../05-API/diagnostics.openapi.yaml).

## Архитектура логирования и регистрация инцидентов

### Структурированные логи приложения

Laravel пишет логи в формате JSON напрямую в стандартный поток ошибок (`stderr`) контейнера. Перед выводом все каналы (включая составной драйвер `stack`) прогоняются через санитайзер `StructuredLogs`. Фильтр на лету вырезает пароли, токены авторизации (Bearer), секреты из вложенных структур, параметров строк запроса и заголовков.

При возникновении исключения в поле `safe_stack` сохраняются максимум двенадцать очищенных фреймов. Сначала идёт файл и строка самого сбоя, затем цепочка вызовов приложения и фреймворка. В каждом фрейме остаются только имя файла, строка, класс и метод. Аргументы вызовов, абсолютные системные пути и сырой текст исключения отсекаются для предотвращения утечек данных.

Имена событий строятся через точку (`event_name`). В зависимости от типа события контекст содержит:
- таймстемп, уровень лога, окружение, имя сервиса и компонента;
- код ошибки и класс исключения;
- идентификаторы запроса (`request_id`), фоновой задачи (`job_id`), прогона ИИ (`llm_run_id`), подготовки отклика и пользователя;
- имя очереди, название задачи, номер попытки, провайдера, операцию, длительность и флаг возможности повтора (`retryable`).

В логи строго запрещено писать: тело HTTP-запросов, тексты резюме, переписку с рекрутерами, вакансии, промпты к ИИ, полные ответы моделей и ключи доступа.

Уровни логирования:

| Уровень | Назначение |
|---|---|
| `DEBUG` | Отладочные детали при локальной разработке. |
| `INFO` | Штатные системные события и переходы бизнес-логики. |
| `WARNING` | Нештатная ситуация, которую система компенсировала самостоятельно. |
| `ERROR` | Завершившаяся сбоем операция пользователя или фонового воркера. |
| `CRITICAL` | Падение критической инфраструктурной зависимости или угроза целостности данных. |

Ошибки пользовательского ввода (валидация 422) и стандартные клиентские ответы 4xx аварийными инцидентами не считаются.

### Сквозная трассировка запросов (Request Tracing)

Nginx отбрасывает пришедший снаружи заголовок `X-Request-ID`, генерирует собственный доверенный идентификатор и пробрасывает его в Laravel. Бэкенд подмешивает этот ID во все лог-записи запроса и отдаёт клиенту в заголовке ответа. При ошибке API возвращает компактный JSON с полями: `error.code`, человекочитаемым безопасным `error.message`, `error.request_id` и булевым флагом `error.retryable`. Ошибки валидации передаются в привычной структуре `errors`.

Неперехваченные исключения HTTP, сбои шедулера и консольных команд регистрируются в центре инцидентов. Консольные команды при сбое генерируют псевдоним вида `cli_…`. Ошибки воркеров очередей и сбои инструментов MCP изолируются отдельными границами диагностики: сбой сохранения инцидента не должен блокировать выполнение основной системной задачи.

В заголовках аварийных ответов клиенту остаются только безопасные поля (`Allow`, `Retry-After`, заголовки рейтлимитов). Любые потенциально опасные заголовки, cookie и токены вырезаются.

### Механика повторов запросов к ИИ

Флаг `retryable` выставляется на основе природы сбоя, а не по сырому HTTP-статусу. Автоматический повтор разрешён при разрыве сетевого соединения, получении 429 от провайдера или временной недоступности (503). Невалидная конфигурация, бан ключа, неполный JSON или отказ модели считаются фатальными ошибками без повтора.

Когда провайдер упирается в квоту, система возвращает код `LLM_PROVIDER_RATE_LIMITED` с `retryable=true`. Если в ответах 429, 408, 425 или 5xx передан корректный заголовок `Retry-After`, воркер засыпает на указанное число секунд (в пределах разумного лимита). При отсутствии заголовка включается экспоненциальный бэкофф с джиттером. Превышение внутренних лимитов самого CVortex отдаёт `RATE_LIMITED`. Кнопка повтора в веб-интерфейсе активна только при флаге `retryable=true`.

Если валидатор отклоняет сгенерированный результат из-за галлюцинаций или битой структуры, пишется код `LLM_OUTPUT_INVALID`. Ошибка привязывается к прогону ИИ (`llm_runs` или `vacancy_llm_runs`) и процессу генерации отклика, сохраняя `user_id` и `request_id`.

### Хранение и дедупликация инцидентов

Таблица `diagnostic_incidents` в PostgreSQL группирует одинаковые сбои и хранит их статус: `OPEN`, `RESOLVED` или `IGNORED`. Каждая группа содержит тип ошибки, признак повторяемости, масштаб влияния и рекомендации по решению. Таблица `diagnostic_occurrences` хранит подробности конкретных срабатываний (очередь, воркер, параметры окружения).

Для повторов из-за лимитов провайдера сохраняется проверенная задержка (от 0 до 86 400 секунд). Задача разбора вакансии удерживает блокировку на время до трёх попыток с учётом максимальной паузы провайдера плюс 10 минут на выполнение. Если одна и та же ошибка происходит в очереди и дублируется в HTTP-ответе, система регистрирует её один раз.

Каждый повтор сбоя инкрементирует счётчик `occurrence_count`. Внутри группы сохраняется глубина до ~1000 последних срабатываний; сборщик мусора запускается каждые 100 новых записей. Если по инциденту в статусе `RESOLVED` прилетает новая ошибка, он автоматически переоткрывается в статус `OPEN`. Статус `IGNORED` остаётся зафиксированным и сам не сбрасывается. Ручная смена статусов оператором протоколируется в `audit_events`.

В панели диагностики доступны фильтры по уровню, статусу, сервису, компоненту, провайдеру ИИ и временному окну. Поиск работает по точным идентификаторам (`request_id`, `job_id`, `llm_run_id`) и кодам ошибок. Обычные пользователи доступа к диагностике не имеют.

### Телеметрия ошибок фронтенда

Клиентские ошибки отправляются из браузера только при активной сессии и живом бэкенде. Разрешены только зарегистрированные компоненты (`browser`, `app-root`, `global-root`). Произвольный текст ошибки, клиентский стек вызовов и переданный с фронтенда `user_id` сервер игнорирует: идентификатор пользователя берётся строго из серверной сессии.

Если сервисы диагностики недоступны, API отдаёт безопасный 503 без ложных подтверждений сохранения.

## Мониторинг очередей и отладка воркеров

Воркеры Horizon обрабатывают асинхронные задачи. Команда `make failed-jobs` запрашивает упавшие задачи через `php artisan diagnostics:failed-jobs`. Полнотекстовое сохранение аргументов упавших задач отключено на уровне Compose; дефолтная таблица `failed_jobs` в проекте не используется во избежание утечки секретов.

Стек вызовов в упавших задачах очищается от системных путей и аргументов, оставляя только место сбоя и кадры вызовов.

Неожиданные 5xx на публичных и внутренних эндпоинтах логируются как инциденты. Если команда `diagnostics:failed-jobs` не может связаться с базой, она отдаёт безопасный код ошибки и завершается с ненулевым статусом без раскрытия SQL-запросов и кредов.

## Инструкция для оператора при расследовании

1. Получите от пользователя безопасный код ошибки, `Reference ID` и примерное время сбоя. Запрашивать пароли, тексты резюме или API-ключи категорически запрещено.
2. Войдите под администратором в `/diagnostics`. Введите точный `Reference ID`, идентификатор запроса или код ошибки. Снимите лишние фильтры, если запись не находится сразу.
3. Ознакомьтесь с полями: «Причина» (`Cause`), «Влияние» (`Impact`), «Рекомендуемое действие» (`Recommended action`) и флагом «Можно ли повторить» (`Retryable`). Сверьте `request_id`, `job_id` и `llm_run_id` с операцией пользователя.
4. Проверьте реальное состояние системы и данных. Только убедившись, что проблема устранена, переводите статус в `RESOLVED`. Если инцидент решено отложить, используйте `IGNORED`.

### Справочник типовых ситуаций

| Симптом | Что проверить | Ожидаемый результат |
|---|---|---|
| Ошибка 500 от API или 503 от провайдера | Найдите `Reference ID`; сверьте `error_code`, таймстемп, провайдера и связанный `llm_run_id`. | В ответе отсутствуют сырые трейсы; повторы сгруппированы в одну запись. |
| Зависло извлечение фактов или разбор вакансии в Horizon | Найдите фоновую задачу; проверьте `llm_run_id` и номер текущей попытки. | Пока действуют повторы провайдера, статус остаётся `PENDING`. При исчерпании попыток статус переходит в `FAILED`, создавая инцидент. |
| Экран сбоя фронтенда в браузере | Найдите `Reference ID` и код `FRONTEND_RUNTIME_ERROR` в окрестности времени сбоя. | Телеметрия уходит только при активной сессии; при падении бэкенда запись появится только в консоли браузера. |
| Отказ в доступе или ошибка валидации 4xx | Сверьте введённые данные, права или срок действия сессии. | Обычные 4xx в инциденты не пишутся и не засоряют центр диагностики. |
| Сбой циклически повторяется | Сравните `occurrence_count`, время первого и последнего срабатывания. | Повторы склеиваются в единую группу; старые детальные записи автоматически ротируются. |
| Запись не найдена или PostgreSQL недоступен | Проверьте состояние контейнеров через `docker compose ps` и снимите логи `backend` и `horizon`. | Поток ошибок Docker (`stderr`) служит надёжным источником логов даже при отказе базы данных. |

Полезные диагностические команды:

```sh
docker compose ps
make logs SERVICE=backend
make logs SERVICE=horizon
make failed-jobs
```

Для форматированного JSON-вывода используйте `make logs-pretty SERVICE=backend` (требует локальный Python 3). Чтобы найти конкретный `request_id` в недавних логах контейнера `backend`:

```sh
docker compose logs --no-color --tail=200 backend | rg --fixed-strings '<request-id>'
```

Помните: Nginx и PostgreSQL пишут собственные логи в обход санитайзера `StructuredLogs`. Перед отправкой фрагментов внешним специалистам проверяйте их на отсутствие чувствительных данных.

## Ротация логов и очистка устаревших записей

Логи контейнеров в Compose пишутся через стандартный драйвер Docker с ротацией (до 5 файлов по 10 МБ на сервис). Они доступны через `docker compose logs` даже при полной недоступности базы данных.

Срок хранения записей в БД задаётся переменными `DIAGNOSTIC_OCCURRENCE_DAYS` (по умолчанию 30 дней) и `DIAGNOSTIC_CLOSED_DAYS` (по умолчанию 90 дней). Планировщик ежедневно запускает очистку через `diagnostics:prune`. Принудительно очистить устаревшие записи можно командой `make diagnostics-prune` (открытые инциденты команда не трогает).

Если веб-интерфейс лёг, порядок действий следующий:

```sh
docker compose ps
docker compose exec -T backend php artisan route:list --path=api/v1/health
make logs SERVICE=backend
make logs SERVICE=frontend
make logs SERVICE=horizon
make failed-jobs
```

Проверьте доступность `/api/v1/health/live` и `/api/v1/health/ready` через локальный порт Nginx, затем найдите `request_id` в логах `backend`. Статус `RESOLVED` фиксирует факт разбора инцидента инженером, но не гарантирует моментального исправления внешней проблемы на стороне ИИ-провайдера. В текущей конфигурации централизованный сборщик логов отсутствует: вся диагностика автономна и локальна.
