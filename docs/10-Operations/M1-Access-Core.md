# Управление доступом M1.1

## Архитектура аутентификации и сессий

В браузере пользовательский запрос проходит маршрут `Next.js → Nginx → Laravel`. За аутентификацию отвечает Laravel Sanctum через сессионные cookie первого лица (first-party stateful auth) в едином доменном пространстве. Никаких JWT, сторонних bearer-токенов или OAuth здесь нет: браузер не держит постоянных токенов в localStorage. Перед авторизацией фронтенд запрашивает `/sanctum/csrf-cookie`, а при мутациях данных отправляет раскодированное значение cookie `XSRF-TOKEN` в заголовке `X-XSRF-TOKEN`.

В конфигурации `SANCTUM_STATEFUL_DOMAINS` прописан макрос `__SANCTUM_CURRENT_REQUEST_HOST__`. Это сохраняет авторизацию через единый источник (same-origin) на любых локальных портах и будущих доменах деплоя, блокируя неавторизованные межсайтовые запросы.

Каждый пользователь обладает:
- публичным идентификатором ULID;
- нормализованным адресом почты (строчные буквы, без пробелов по краям);
- надёжным хэшем пароля (Argon2id или bcrypt);
- ролью (`admin` либо `user`);
- статусом аккаунта (`ACTIVE` либо `DISABLED`).

Laravel валидирует email правилом `email:rfc`. Для сравнения система приводит адрес к нижнему регистру и отсекает пробелы; проверку MX-записей или реального существования домена CVortex не проводит.

При каждом запросе авторизованного пользователя middleware проверяет статус аккаунта: он обязан быть `ACTIVE`. При отключении учётной записи все её активные сессии в базе немедленно аннулируются. Роль `admin` не даёт права читать или менять чужие карьерные данные. Любой закрытый эндпоинт API обязан сверять `user_id` из сессии с владельцем сущности в базе и отвечать `404 Not Found`, если запись принадлежит другому пользователю (защита от IDOR).

## Команды оператора

Все административные команды запускаются внутри контейнера `backend`. При создании первого администратора ввод пароля скрыт: он не отображается в терминале и не попадает в журналы аудита.

```bash
docker compose exec backend php artisan user:bootstrap-admin admin@example.test
```

Если администратор в системе уже зарегистрирован, команда завершится без изменений.

Ниже приведены команды управления инвайтами и пользователями (подставьте реальные идентификаторы вместо плейсхолдеров `INVITATION_ULID` и `USER_ULID`):

```bash
docker compose exec backend php artisan invitation:create --email=person@example.test --expires=7
docker compose exec backend php artisan invitation:create --expires=7
docker compose exec backend php artisan invitation:revoke INVITATION_ULID
docker compose exec backend php artisan user:disable USER_ULID
docker compose exec backend php artisan user:enable USER_ULID
```

Команда `invitation:create` генерирует идентификатор инвайта (он нужен для отзыва) и одноразовую ссылку для регистрации. Срок жизни инвайта по умолчанию составляет 7 дней (настраивается от 1 до 30 дней). Сам секретный токен состоит из 32 криптографически стойких случайных байт в hex-формате. В базе хранится только его HMAC-SHA-256 хэш, а сырой токен оператор видит ровно один раз при создании ссылки: `/register#token=<value>`.

Страница регистрации `/register` считывает токен из фрагмента URL (`#`), держит его исключительно в оперативной памяти страницы и сразу вычищает из адресной строки браузера через `history.replaceState`. При отправке формы токен уходит только в JSON-теле POST-запроса. Он не оседает в параметрах запроса, логах прокси, localStorage или заголовке `Referer`.

## Модель данных, изоляция и аудит

Нормализация email и валидация одинаково работают для веб-запросов и CLI-команд.

Регистрация по инвайту выполняется в единой транзакции с блокировкой записи инвайта (`SELECT ... FOR UPDATE`): система проверяет срок действия, соответствие email (если инвайт персональный) и уникальность пользователя в базе. Затем создаётся аккаунт, инвайт помечается использованным, и пишется событие аудита. При попытке одновременной регистрации по двум разным инвайтам на один email одна транзакция пройдёт успешно, а вторая откатится с HTTP 422 по уникальному индексу.

Прикладной код может создавать события аудита, но не имеет права их модифицировать или удалять. Класс `AuditEventQueryBuilder` разрешает запись через `AuditLogger`, но намертво блокирует вызовы `update()`, `delete()`, `forceDelete()`, `truncate()`, `upsert()`, `updateOrInsert()`, `increment()`, `decrement()` и `touch()`. Это ограничение на уровне ORM. (Прямые SQL-запросы через фасад `DB` в приложении запрещены соглашениями).

В журнал аудита пишутся: актор (`USER`, `OPERATOR`, `SYSTEM`), его идентификатор, тип действия и очищенные метаданные. Система автоматически вырезает пароли, токены инвайтов, сессионные ID и CSRF-токены из защищённых полей.

Команда инициализации первого администратора захватывает advisory lock на уровне PostgreSQL на время транзакции, исключая гонку при параллельном запуске. SQLite в юнит-тестах пропускает advisory lock из-за отсутствия аналога в однопроцессной СУБД; параллельные сценарии верифицируются на реальном PostgreSQL.

Частота попыток входа ограничена рейлимитом `login`. Дефолт CVortex: 5 попыток за 60 секунд (настраивается через `AUTH_LOGIN_RATE_LIMIT_ATTEMPTS` и `AUTH_LOGIN_RATE_LIMIT_DECAY_SECONDS`). Счётчик привязан к связке нормализованного email и IP-адреса клиента. При исчерпании лимита API возвращает HTTP 429.

Сценарий многопоточной проверки на реальной СУБД запускается скриптом `scripts/test-access-core-postgres-concurrency.sh`. Он создаёт временную базу, симулирует гонки при регистрации и создании админа, после чего чисто удаляет тестовые данные.

## Результаты приёмки M1.1

Исторические данные локальной верификации доработок по замечаниям PR #23:
- PHPUnit: 40 тестов, 180 ассертов — зелёный статус.
- Vitest: 2 теста, 2 ассерта — успешно.
- Линтеры: Pint проверил 48 файлов без замечаний, Larastan прошёл без ошибок.
- Тест конкурентности PostgreSQL подтвердил защиту от гонок при создании админа, использовании инвайта и одновременной регистрации на один адрес.
- Проверка цепочки same-origin авторизации подтвердила последовательность статусов `204/201/204/200/204/401`.
- Production-сборка фронтенда, накат и откат миграций завершились успешно.

Сборка фронтенда в режиме разработки (`NODE_ENV=development`) внутри Compose может падать с ошибкой `useContext(null)` при пререндере `/_global-error`. Сборка с `NODE_ENV=production` отрабатывает стабильно. Предупреждения Compose о незаданных переменных в dev-окружении известны и зафиксированы в бэклоге.

Отсутствие `pnpm-lock.yaml` и нюансы пакетного менеджера вынесены в отдельный технический долг репозитория вне рамок M1.1.

### Миграция на новый алгоритм хэширования паролей

При смене `HASH_DRIVER` требуется плавная миграция. На переходный период выставьте `HASH_VERIFY=false`, чтобы фреймворк мог сверять старые хэши. При успешном логине пароль пользователя автоматически перехэшируется новым алгоритмом. Когда все активные пользователи обновят хэши, верните `HASH_VERIFY=true` и перезапустите бэкенд. Включать строгую проверку до завершения миграции нельзя.
