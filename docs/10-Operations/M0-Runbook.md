# Операционная инструкция M0

Экспресс-ранбук дежурного инженера для оперативного контроля локального стека M0.

## Экспресс-диагностика

```sh
docker compose ps
health_authority="$(docker compose port nginx 80)"
curl -i "http://${health_authority}/api/v1/health/live"
curl -i "http://${health_authority}/api/v1/health/ready"
make logs SERVICE=backend
make logs SERVICE=horizon
```

В штатном режиме `/live` отдаёт `{"status":"live"}`, а `/ready` возвращает `{"status":"ready"}`.
- Проверка `/live` подтверждает, что цепочка Nginx → PHP-FPM/Laravel жива и отвечает на запросы.
- Проверка `/ready` дополнительно пингует PostgreSQL и Redis с жёстким тайм-аутом. Если база или кэш недоступны, эндпоинт вернёт HTTP 503 и `{"status":"not_ready"}`.

## Разбор типовых сбоев

- **Конфликт портов:** порт 8080 (или другой заданный) занят соседним приложением. Задайте свободный `CVORTEX_PORT` и синхронный `APP_URL` в корневом `.env`, затем перезапустите стек через `make up`. Не гасите неизвестные системные процессы вслепую.
- **Эндпоинт готовности отдаёт 503:** проверьте статусы контейнеров через `docker compose ps` и снимите логи зависимостей: `make logs SERVICE=postgres`, `make logs SERVICE=redis`, `make logs SERVICE=backend`. Поднимите упавшую службу и повторите запрос к `/ready`. Перезапускать сам бэкенд обычно не требуется.
- **PostgreSQL здоров в docker ps, но приложение не стартует:** убедитесь, что база из `POSTGRES_DB` в вашем `.env` реально существует внутри смонтированного тома. Зелёный healthcheck контейнера гарантирует лишь доступность СУБД, но не доказывает наличие базы данных или валидность прав роли `cvortex_app`. Пошаговый сценарий безопасной проверки описан в руководстве [«Локальная установка и запуск»](Local-Development.md).
- **Сбоит воркер Horizon:** убедитесь в доступности Redis и изучите логи через `make logs SERVICE=horizon`. После починки Redis проверьте статус воркера: `docker compose exec horizon php artisan horizon:status`.
- **Повреждены или отсутствуют зависимости:** накатите `make init` заново. Скрипт подтянет зафиксированные версии зависимостей без перезаписи вашего текущего `.env`.
- **Нужно чисто перезагрузить службы:** выполните `make restart`. Docker аккуратно пересоздаст контейнеры в правильной последовательности без потери данных в томах.

## Проверка качества и сборки

```sh
docker compose --env-file .env.example config --quiet
make lint
make test
docker compose build frontend
```

Этот же набор проверок прогоняется в пайплайне CI. Восстановление после сбоя инфраструктурных сервисов и сохранность данных в томах верифицируются вручную при приёмке этапа M0.

## Персистентность и сохранность данных

Штатная остановка через `make down` сохраняет все Docker-тома. База PostgreSQL и приватные файлы из каталога `storage/app/private` надёжно защищены от случайного удаления при перезапуске контейнеров. Данные Redis принципиально эфемерны и сбрасываются. Никогда не используйте команды очистки томов (`--volumes`), если не планируете полностью обнулить локальную базу и хранилище.
