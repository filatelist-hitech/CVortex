Твоя задача — исследовать существующий проект CVortex, спроектировать и реализовать полноценную систему автоматизированного тестирования пользовательского интерфейса на Playwright.

# 2. Product Context

CVortex — персональная Job Search OS.

Основной слоган:

Your career, in context.

Продукт помогает пользователю:

- хранить Career Profile и Career Facts;
- импортировать резюме;
- подтверждать и редактировать извлечённые карьерные факты;
- создавать Career Tracks;
- импортировать и анализировать вакансии;
- оценивать соответствие кандидата требованиям вакансии;
- принимать решение о целесообразности отклика;
- адаптировать резюме;
- создавать сопроводительные письма;
- хранить историю откликов;
- управлять компаниями и Employer Memory;
- хранить историю общения с рекрутерами;
- готовиться к интервью;
- генерировать DOCX/PDF;
- анализировать эффективность поиска работы.

Архитектурное направление проекта:

- Backend: PHP 8.4+, Laravel.
- Frontend: Next.js, React, TypeScript.
- API: REST.
- Database: PostgreSQL.
- Queue/cache: Redis и Laravel Horizon.
- Infrastructure: Docker Compose, Nginx.
- Documents: DOCX templates и LibreOffice headless.
- Initial mobile strategy: responsive PWA.
- UI automation: Playwright.

Это описание задаёт контекст, но не доказывает, что все перечисленные функции уже реализованы.

Фактическое состояние репозитория, принятые ADR, API contracts и действующая документация являются источниками истины.

# 3. Core Product Invariants

Все тесты должны учитывать ключевые принципы CVortex.

## 3.1 Truth-first

CVortex не должен придумывать карьерные факты пользователя.

Generated Content должен быть связан с подтверждёнными фактами через цепочку:

FACT → CLAIM → CONTENT.

Если функциональность реализована, тесты должны проверять, что:

- неподтверждённые Career Facts не становятся подтверждёнными автоматически;
- генерация не использует запрещённые неподтверждённые факты;
- пользователь может подтвердить, отредактировать или отклонить предложенный факт;
- содержимое generated documents соответствует действующим правилам Truth Guard.

Не проверяй только наличие текста в интерфейсе. Проверяй фактическое поведение системы.

## 3.2 Consistency-first

История взаимодействий с одним работодателем должна учитываться при подготовке новых материалов.

Если реализована проверка противоречий, тестируй:

- обнаружение противоречия;
- отображение причины;
- блокирование запрещённой генерации;
- возможность разрешения конфликта предусмотренным способом;
- отсутствие ложного автоматического разрешения конфликта.

## 3.3 Human approval

CVortex не должен автоматически отправлять отклики работодателям.

Если интерфейс позволяет создавать резюме, сопроводительные письма или другие материалы, проверь, что пользователь может просмотреть результат и подтвердить необходимые изменения.

Не считай кнопку Approve доказательством безопасности. Проверяй реальный переход состояния и сохранение результата.

## 3.4 Multi-user isolation

Private resources одного пользователя не должны быть доступны другому пользователю.

Это относится к:

- Career Facts;
- Career Profiles;
- Applications;
- Vacancies, если они приватные;
- Documents;
- Conversations;
- Employer Memory;
- LLM credentials;
- настройкам пользователя;
- другим приватным сущностям приложения.

Проверяй изоляцию через реальный UI и доступные пользовательские маршруты.

## 3.5 Deterministic before AI

Не полагайся на случайный вывод LLM там, где ожидаемое поведение можно проверить детерминированно.

Тесты не должны зависеть от конкретной формулировки, выбранной моделью, если эта формулировка не является частью утверждённого контракта.

- design system;
- Figma references, если они доступны в проекте.

Используй существующие соглашения и инфраструктуру.

Не создавай новые инструменты, если эквивалентные уже существуют.

## 7.2 Build a Route Inventory

Создай реестр всех существующих UI routes.

Для каждой страницы зафиксируй:

- route;
- purpose;
- authentication requirement;
- required role;
- primary actions;
- secondary actions;
- forms;
- relevant API operations;
- empty state;
- loading state;
- success state;
- error state;
- authorization behavior;
- responsive requirements;
- planned Playwright coverage.

Для динамических маршрутов учитывай валидные и невалидные идентификаторы.

Для защищённых страниц учитывай неавторизованного пользователя.

## 7.3 Build a Feature Inventory

Сопоставь UI с документацией.

Каждую функциональность отнеси к одной из категорий:

IMPLEMENTED

Функциональность реализована и доступна для тестирования.

PARTIALLY_IMPLEMENTED

Есть только часть ожидаемого поведения.

DOCUMENTED_NOT_IMPLEMENTED

Функциональность присутствует в требованиях, но отсутствует в реализации.

BLOCKED

Функциональность невозможно протестировать по конкретной технической причине.

NOT_APPLICABLE

Функциональность не относится к текущей версии продукта.

Не выдавай `DOCUMENTED_NOT_IMPLEMENTED` за покрытый тестами сценарий.

## 7.4 Coverage Matrix

Создай:

`docs/09-QA/playwright-coverage-matrix.md`

Минимальные поля:

| Field | Meaning |
|---|---|
| Feature | Функциональность |
| Route | UI route |
| Scenario | Проверяемое поведение |
| Priority | P0/P1/P2/P3 |
| Type | Positive/Negative/Boundary/Security/Accessibility/Responsive |
| Status | Covered/Partial/Uncovered/Blocked/N/A |
| Test file | Путь к тесту |
| Notes | Пробелы или ограничения |

Coverage matrix является основным способом измерения полноты тестирования.

Line coverage сама по себе не доказывает полноту UI/E2E-покрытия.

# 8. Phase B — Playwright Architecture

После аудита выбери расположение Playwright в соответствии с текущей архитектурой.

Предпочтительная отправная точка для monorepo:

`apps/frontend/playwright.config.ts`

и тесты внутри frontend application.

Но сначала проверь существующую структуру.

Не создавай одновременно несколько конкурирующих Playwright configurations.

## 8.1 Playwright Configuration

Настрой:

- baseURL;
- browser projects;
- test directory;
- global setup, если он необходим;
- webServer только для подходящего локального окружения;
- timeout policy;
- assertion timeout;
- trace;
- screenshots;
- video policy;
- reporters;
- retries;
- workers;
- environment configuration;
- test tags.

Configuration должна работать локально и в CI.

Не зашивай абсолютные пути и личные настройки разработчика.

## 8.2 Browser Strategy

Минимальный обязательный профиль:

Chromium desktop.

Добавь отдельный mobile viewport project, если он полезен для текущего responsive UI.

Firefox и WebKit подключай, если существующие dependencies, инфраструктура и требования позволяют это сделать.

Предпочтительная стратегия:

- pull request: быстрые smoke tests и основные Chromium E2E;
- полный CI: полный основной набор;
- дополнительный browser matrix: критические workflows;
- расширенный regression suite: по расписанию или перед релизом.

Не запускай дорогой полный browser matrix для каждого незначительного изменения без обоснования.

Если браузер не поддерживается текущим приложением или окружением, документируй причину.

## 8.3 Project Scripts

Добавь согласованные команды, используя текущий package manager.

Предпочтительные имена:

- `test:e2e`
- `test:e2e:ui`
- `test:e2e:headed`
- `test:e2e:debug`
- `test:e2e:smoke`
- `test:e2e:critical`
- `test:e2e:report`

Это примеры целевых команд. Адаптируй их к существующим scripts.

Не ломай имеющиеся команды.

Раздели наборы по назначению:

Проверяют, что приложение запускается и основные маршруты доступны.

### Critical E2E

Проверяют основные пользовательские workflows от начала до конца.

Проверяют расширенные сценарии и известные риски.

Проверяют доступность ключевых интерфейсов.

Проверяют критические страницы на мобильных viewport.

### Failure Handling

Не копируй один и тот же тест в несколько файлов только ради разных наборов.

# 10. Locator Strategy

Используй устойчивые и доступные локаторы.

Приоритет:

1. `getByRole`
2. `getByLabel`
3. `getByPlaceholder`, когда placeholder является частью UX
4. `getByText`, когда текст является частью проверяемого поведения
5. `getByTestId`, когда семантического локатора недостаточно

Не используй хрупкие CSS selectors и XPath без необходимости.

Не завязывайся на внутреннюю структуру DOM, случайные CSS-классы или позицию элемента.

Не добавляй `data-testid` ко всем элементам.

Добавляй test IDs только для действительно неоднозначных или технически значимых элементов.

Если accessibility проблемы мешают устойчивому тестированию, исправляй их минимально и документируй.

## 10.1 Assertions

Проверяй фактическое поведение.

Например, после нажатия Save необходимо проверить:

- что запрос завершился ожидаемым результатом;
- что интерфейс показал правильное состояние;
- что данные сохранились;
- что после перезагрузки они остаются доступными, если это предусмотрено контрактом.

Не ограничивайся `toBeVisible()` для кнопки Save.

# 11. Test Data and Isolation

Создай детерминированную систему подготовки тестовых данных.

## 11.1 Synthetic Data Only

Используй вымышленные:

- имена;
- email;
- компании;
- вакансии;
- карьерные факты;
- документы;
- переписки;
- интервью;
- API responses.

Не используй настоящие персональные данные.

Не копируй production records в fixtures.

## 11.2 Test Users

Если приложение поддерживает роли, создай изолированные test identities.

Минимальный набор:

- admin;
- user A;
- user B;
- unauthenticated visitor.

Дополнительные identities создавай при необходимости.

Не используй один общий изменяемый аккаунт для параллельных тестов.

Для каждого теста, изменяющего данные, обеспечь независимое состояние.

## 11.3 Data Lifecycle

Предусмотри:

- создание необходимых fixtures;
- подготовку исходного состояния;
- очистку созданных ресурсов;
- защиту от конфликтов при параллельном запуске;
- повторный запуск без ручной очистки;
- возможность повторить упавший тест.

Используй существующий test seeding mechanism, если он есть.

Не добавляй публичные production endpoints для сброса базы или подготовки тестов.

Если требуется test-only helper, он должен быть недоступен в production configuration.

## 11.4 Database Safety

Запрещено направлять тесты на production database.

Не выполняй destructive reset против обычной developer database без проверки окружения.

Если тестовое окружение не настроено:

- определи необходимую конфигурацию;
- создай безопасный test setup;
- документируй требуемые переменные;
- завершай тесты с понятной ошибкой при опасной конфигурации.

# 12. Authentication and Authorization Coverage

Если authentication реализована, покрой все существующие способы входа и регистрации.

## 12.1 Registration

Проверь:

- валидную регистрацию;
- обязательные поля;
- отсутствующие поля;
- некорректный email;
- слишком короткие или длинные значения;
- несовпадающие пароли, если применимо;
- повторный email;
- повторную отправку формы;
- отображение серверных validation errors;
- защиту от двойного создания пользователя.

## 12.2 Invite-only Registration

Если действует invite-only модель, проверь:

- валидное приглашение;
- отсутствующий token;
- некорректный token;
- истёкший token;
- уже использованное приглашение;
- исчерпанный usage limit;
- привязку к email, если она предусмотрена;
- повторную попытку использования;
- параллельные попытки использовать одно приглашение.

Проверяй не только сообщение об ошибке, но и то, что запрещённый пользователь действительно не создан.

## 12.3 Login

Проверь:

- валидные credentials;
- неверный пароль;
- неизвестный пользователь;
- пустые поля;
- некорректный email;
- обработку серверной ошибки;
- повторную отправку;
- предусмотренное поведение при rate limiting;
- корректное состояние сессии.

## 12.4 Logout and Sessions

Проверь:

- logout;
- невозможность открыть защищённый маршрут после logout;
- корректный redirect;
- отсутствие утечки приватного содержимого после logout;
- истечение сессии, если такое поведение можно воспроизвести;

# 31. Deterministic LLM Testing

Это обязательное требование CVortex.

Тесты не должны зависеть от:

- доступности OpenAI API;
- реальных API keys;
- случайных model outputs;
- текущих model prices;
- лимитов пользовательского аккаунта;
- внешних вакансий;
- нестабильного сетевого окружения.

## 31.1 Provider Strategy

Изучи существующую LLM abstraction.

Если есть provider abstraction и fake/test implementation, используй их.

Если нет, предложи минимальный test seam, совместимый с архитектурой.

Предпочтительные способы:

- fake LLM provider;
- deterministic test provider;
- фиксированные provider responses;
- test fixtures;
- controllable backend stubs.

Не создавай параллельную бизнес-логику специально для тестов.

## 31.2 LLM Invariants

Для generated content проверяй:

- валидность output schema;
- использование подтверждённых фактов;
- отсутствие неподтверждённых claims;
- корректную связь claims с evidence;
- язык;
- ожидаемое поведение при недостатке данных;
- корректную обработку отказа provider;
- обработку malformed output;
- повторную попытку;
- controlled failure.

Не требуй буквального совпадения естественного текста.

## 31.3 Test Profiles

Используй synthetic scenarios:

- обычная успешная генерация;
- пустой ответ;
- malformed structured output;
- timeout;
- rate limit;
- provider unavailable;
- conflict detected;
- missing evidence;
- unconfirmed Career Fact;
- valid response after retry.

Если сценарий не поддерживается текущей архитектурой, документируй необходимый минимальный seam.

---

# 32. API and External Service Boundaries

Для полноценного E2E не мокай весь собственный backend.

Критические пользовательские сценарии должны проходить через настоящий frontend и настоящий backend соответствующего тестового окружения.

Используй реальную persistence layer тестового окружения там, где она необходима для проверки бизнес-поведения.

Допускается контролируемое мокирование:

- внешних job boards;
- сторонних сайтов;
- внешних API;
- LLM providers;
- нестабильных внешних сервисов.

Для frontend-specific error scenarios допускается контролируемый перехват запросов, если это не выдаётся за полный backend E2E.

Чётко различай:

- полноценный E2E;
- UI integration test с мокированным API;
- тест внешней интеграции.

Не смешивай их в отчётах покрытия.

---

# 33. Test Quality and Flakiness

Тесты должны быть повторяемыми.

Обязательные правила:

- не использовать произвольные `waitForTimeout` как основную синхронизацию;
- использовать Playwright auto-waiting;
- использовать web-first assertions;
- избегать зависимости от порядка тестов;
- не использовать shared mutable test accounts без изоляции;
- не оставлять созданные ресурсы после завершения теста;
- не подавлять неожиданные ошибки приложения;
- не добавлять retries ради маскировки нестабильности;
- не отключать assertions для flaky scenarios;
- не использовать чрезмерные глобальные timeouts;
- не зависеть от реального времени, если его можно контролировать.

Если тест падает нестабильно:

1. найди причину;
2. исправь синхронизацию или изоляцию;
3. повтори тест;
4. документируй оставшиеся ограничения.

Retries должны помогать диагностике, а не заменять исправление.

---

# 34. Page Objects and Helpers

Используй Page Objects только там, где они упрощают поддержку.

Не создавай огромный универсальный Page Object, управляющий всем приложением.

Не оборачивай каждый Playwright method в отдельный abstraction без необходимости.

Предпочитай:

- domain-specific fixtures;
- небольшие reusable helpers;
- понятные page objects для сложных страниц;
- простые независимые tests.

Тест должен оставаться понятным без необходимости переходить через десять уровней abstractions.

---

# 35. Coverage Strategy

Используй risk-based testing.

Приоритеты:

## P0 — Critical

- login;
- authorization;
- cross-user isolation;
- критические data mutations;
- подтверждение карьерных фактов;
- Truth Guard;
- application state changes;
- доступ к приватным документам;
- безопасность LLM credentials;
- сохранение и генерация документов, если эти workflows реализованы.

## P1 — High

- основные CRUD workflows;
- импорт вакансий;
- matching;
- resume recommendations;
- cover letters;
- Employer Memory;
- основные формы;
- основные error states.

## P2 — Medium

- фильтры;
- сортировка;
- pagination;
- менее критичные настройки;
- дополнительные состояния компонентов;
- расширенные responsive scenarios.

## P3 — Low

- некритичные визуальные детали;
- второстепенные edge cases;
- низкорисковые UI variations.

Приоритет не освобождает от тестирования требований безопасности.

## 35.1 Test Design

Для каждого важного поля и workflow рассмотри:

- valid input;
- invalid input;
- missing input;
- boundary values;
- duplicate operation;
- repeated submission;
- permission denied;
- server error;
- persistence;
- cancellation;
- retry.

Не создавай все возможные комбинации механически.

Используй equivalence partitioning, boundary-value analysis и pairwise coverage там, где это оправдано.

---

# 36. CI Integration

Интегрируй Playwright в существующий CI.

Не создавай конкурирующий pipeline без необходимости.

CI должен обеспечивать:

1. подготовку изолированного test environment;
2. запуск необходимых services;
3. создание test data;
4. установку browser dependencies;
5. запуск smoke tests;
6. запуск критических E2E;
7. сохранение отчётов;
8. сбор диагностических артефактов при падениях.

Используй существующую CI-платформу.

Если это GitHub Actions, расширяй текущие workflows.

Не запускай production deployment.

## 36.1 Artifacts

При падении сохраняй подходящие артефакты:

- Playwright HTML report;
- trace;
- screenshot;
- video, если включено соответствующей политикой;
- JUnit report, если он используется CI.

Не сохраняй в artifacts секреты, реальные персональные данные или чувствительное содержимое пользовательских документов.

---

# 37. Observability and Diagnostics

Каждый упавший тест должен давать достаточно информации для диагностики.

Отчёт должен содержать:

- test title;
- route;
- browser/project;
- expected behavior;
- actual failure;
- stack trace;
- relevant Playwright trace;
- screenshot, если доступен;
- correlation information, если её безопасно получить.

Не выводи API keys, cookies, authentication tokens и другие secrets в логи.

Не прикладывай полное содержимое приватных документов без необходимости.

---

# 38. Performance Considerations

Не превращай Playwright suite в случайный benchmark.

Не добавляй жёсткие performance assertions без существующих требований и контролируемого окружения.

Допускается проверять:

- отсутствие бесконечной загрузки;
- завершение критического workflow в разумном test timeout;
- отсутствие зависших dialogs;
- отсутствие повторных запросов, если это нарушает контракт;
- отсутствие очевидных блокирующих ошибок.

Если performance testing необходим, отдели его от обычного функционального E2E.

---

# 39. Definition of Done

Задача не считается завершённой только потому, что Playwright установлен и один тест проходит.

Необходимо выполнить следующие критерии.

## A. Inventory

- [ ] Все существующие UI routes инвентаризированы.
- [ ] Все основные пользовательские workflows перечислены.
- [ ] Для каждой важной функции определён статус реализации.
- [ ] Создана coverage matrix.
- [ ] Пробелы между документацией и реализацией зафиксированы.

## B. Infrastructure

- [ ] Playwright установлен или существующая конфигурация улучшена.
- [ ] Configuration работает локально.
- [ ] Есть отдельное безопасное test environment.
- [ ] Test data изолированы.
- [ ] Параллельный запуск не вызывает конфликтов.
- [ ] Отчёты доступны.
- [ ] Диагностика падений настроена.
- [ ] Команды запуска документированы.

## C. Functional Coverage

- [ ] Все основные существующие routes покрыты smoke tests.
- [ ] Все реализованные P0 workflows имеют E2E coverage.
- [ ] Основные P1 workflows покрыты.
- [ ] Для ключевых форм проверены положительные и отрицательные сценарии.
- [ ] Проверены основные loading, empty, success и error states.
- [ ] Проверено сохранение критических изменений.
- [ ] Проверена обработка повторных действий.

## D. Security

- [ ] Проверены основные authorization boundaries.
- [ ] Добавлены отрицательные cross-user tests.
- [ ] Проверены защищённые маршруты.
- [ ] Проверены приватные документы.
- [ ] Проверены чувствительные настройки, если они существуют.
- [ ] Тесты не используют production data или реальные secrets.

## E. Responsive and Accessibility

- [ ] Проверены основные desktop workflows.
- [ ] Проверены основные mobile workflows.
- [ ] Выполнены accessibility checks для ключевых страниц.
- [ ] Найденные нарушения зафиксированы.
- [ ] Визуальные проверки не маскируют функциональные ошибки.

## F. LLM

- [ ] AI-тесты используют детерминированные ответы.
- [ ] Нет обязательной зависимости от реального LLM API.
- [ ] Проверены Truth Guard invariants там, где функциональность реализована.
- [ ] Проверена обработка provider failures.
- [ ] Generated content не тестируется исключительно exact-string assertions.

## G. Quality

- [ ] Тесты повторяемы.
- [ ] Нет необъяснимых skipped tests.
- [ ] Нет незаполненных TODO, скрывающих обязательные проверки.
- [ ] Нет массового использования `waitForTimeout`.
- [ ] Нет необоснованных глобальных timeouts.
- [ ] Нет unrelated product refactoring.
- [ ] Изменённая конфигурация проверена.
- [ ] Документация обновлена.
- [ ] Project state обновлён.

## H. Validation

- [ ] Запущен smoke suite.
- [ ] Запущен critical E2E suite.
- [ ] Запущен полный реализованный набор, если позволяет окружение.
- [ ] Typecheck/lint выполнены, если применимо.
- [ ] Все обязательные тесты проходят либо блокирующие дефекты явно перечислены.

Не отмечай проверку как пройденную, если она не была выполнена.

Если критерий невозможно выполнить, укажи точную причину и оставшийся риск.

# 42. Execution Protocol

Работай последовательно.

## Step 1 — Audit

Изучи существующую архитектуру и тесты.

Составь route inventory, feature inventory и coverage matrix.

## Step 2 — Test Architecture

Определи:

- расположение Playwright;
- configuration;
- test environment;
- fixture strategy;
- authentication strategy;
- test data lifecycle;
- browser matrix;
- CI integration.

Зафиксируй решения.

## Step 3 — Infrastructure

Реализуй базовую конфигурацию и безопасное тестовое окружение.

Проверь, что хотя бы один настоящий UI smoke test выполняется.

## Step 4 — Critical Flows

Покрой P0 workflows.

Начни с authentication, authorization, navigation и основных пользовательских операций, которые действительно существуют.

## Step 5 — Feature Coverage

Последовательно покрывай остальные реализованные функции.

Не перескакивай между независимыми модулями без необходимости.

## Step 6 — Error and Boundary Coverage

Добавь отрицательные сценарии, boundary tests, error states и проверку повторных действий.

## Step 7 — Responsive and Accessibility

Проверь критические страницы на мобильных viewport и accessibility.

## Step 8 — CI and Reports

Подключи suite к CI и настрой артефакты.

## Step 9 — Full Validation

Запусти полный доступный набор.

Исправь проблемы тестовой инфраструктуры и дефекты в пределах разрешённого scope.

## Step 10 — Final Coverage Review

Сопоставь фактические тесты с coverage matrix.

Не оставляй ложных отметок Covered.

Перечисли оставшиеся пробелы и риски.

После этого обнови документацию и project state.

---

# 43. Resource Discipline

Не загружай все документы и файлы репозитория в контекст без необходимости.

Используй:

- documentation indexes;
- route inventory;
- coverage matrix;
- релевантные ADR;
- targeted source inspection.

Не перечитывай каждый раз все существующие документы.

Не запускай тяжёлый полный suite после каждого изменения одного теста.

Используй последовательность:

targeted test
→ relevant suite
→ full suite.

Не создавай многочисленные test helpers заранее, если пока нет подтверждённой необходимости.

Не добавляй dependencies ради гипотетических сценариев.

---

# 44. Final Report

В конце предоставь краткий, но точный отчёт.

## Result

PASS / PARTIAL / BLOCKED.

## Test Infrastructure

Что создано и как запускается.

## Coverage

- количество существующих UI routes;
- количество инвентаризированных функций;
- количество реализованных тестовых сценариев;
- количество P0 сценариев с покрытием;
- количество P1 сценариев с покрытием;
- количество непокрытых критических сценариев;
- количество обнаруженных блокирующих дефектов.

Не выдумывай числа.

Показывай метод подсчёта, если показатели могут интерпретироваться неоднозначно.

## Tests

Перечисли выполненные команды и фактические результаты.

Отдельно укажи:

- passed;
- failed;
- skipped;
- not executed.

## Files

Основные созданные и изменённые файлы.

## Security

Какие security scenarios проверены и какие ограничения остались.

## Known Gaps

Какие функции не реализованы или не покрыты.

## Next Step

Один рекомендуемый следующий bounded step.

Не переписывай в отчёте всю документацию.
